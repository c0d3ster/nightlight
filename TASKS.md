A stack is a milestone; there is no separate plan or phase level, and `solo` tasks get no milestone. Linear milestones only exist inside a Project, so resolve the container as: `linear.projectId` from the meta file if set (used as is; it must belong to the repo's team), else find a Project in the team named after the repo with `list_projects`, else create one with `save_project`. Never create a duplicate: look up by name first. Create the Project and milestones only in `/plan-tasks`, which is interactive, and list "will create Linear Project X and milestone Y" in its approval proposal; overnight runs and housekeeping only read the Project and complete or reopen milestones (complete when the stack is finished, reopen on resume), and housekeeping may record the resolved project id in the meta file in its existing commit. `/plan-tasks` sets the milestone on each issue via `save_issue`. The `nl:stack:<name>` label stays authoritative for dispatch. Inspect the parameters of `list_projects`, `save_project`, `list_milestones`, and `save_milestone` first (names from `docs/research/linear-mcp.md`, parameters not yet checked), and add narrow allow entries only for tools used. Not sub-issues (a stack is ordered siblings, not one parent) and not Initiatives. Decided 2026-11-02; depends on the Linear stack (`#22` to `#26`).
- [ ] Document one Linear team per repo as the supported setup, and warn about sharing a team. A team per repo (inside one workspace) gives each repo its own issue prefix, statuses, cycles, and labels, and avoids a second API key or MCP sign-in (the MCP connects to one workspace at a time). Add this to the README and CLAUDE.md Linear sections and to `migrate --to linear`'s setup step; check whether the Linear plan limits the number of teams and whether `nl:*` labels should be workspace-wide or team-scoped when created. Found in design discussion, 2026-11-02.
