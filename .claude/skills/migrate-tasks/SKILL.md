---
name: migrate-tasks
description: Moves a target repo's open TASKS.md items, including Decisions (`nl:decision`) and Discovered (`nl:discovered`), into GitHub issues or Linear issues (`--to github` or `--to linear`, local to remote only), archives its checked-off items, removes TASKS.md when nothing remains, then flips taskSource. In GitHub mode it also reviews unlabeled existing issues for staleness (shared with `/tidy-issues`, `pnpm tidy`). Every create, close, and relabel needs per-item approval.
disable-model-invocation: true
---

A target repo is attached via --add-dir; args are `--to github` or `--to linear`. `--to linear`: skip everything below and follow "Linear mode" at the end. GitHub-to-local is out of scope. Nothing is created, closed, edited, or relabeled without my explicit per-item approval. Announce each phase in one line before starting it.

## Setup

1. Read the repo's `docs/nightlight-meta.json`. Open items (`- [ ]`, `- [!]`, `- [/]`) in TASKS.md, in any section including Decisions and Discovered, decide whether migration is needed, not the flag: `taskSource` can be set to `github` by hand or by an earlier step without the backlog having moved. `taskSource` already `github` and no open or checked-off (`- [x]`) items: nothing to migrate. Stop, and tell me `pnpm tidy <repo>` reviews the repo's existing unlabeled issues. `taskSource` already `github` with open or checked-off items: partial migration, run every phase and skip only the `taskSource` flip in Phase 4 step 5. Otherwise, missing TASKS.md or no open items: skip the dedupe and create work for open items (Phase 1 steps 1-4 and Phase 2) and go to phase 3. Checked-off items are never turned into issues; they are archived in Phase 4, so Phase 1 step 5 and Phase 4 still run for them.
2. Resolve the issue repo: `github.repo` from the meta file, else origin (`gh repo view --json nameWithOwner`). Load the module from the nightlight checkout: `source lib/task-source.sh`, then set `TS_GITHUB_REPO` and use `ts_find_related` and `ts_gh_label` from `lib/task-source-github.sh` (source it directly; the meta file may not be `github` yet). Label names come from `ts_gh_label` (defaults `nl:agent-ready`, `nl:verify`, `nl:research`, `nl:blocked`, `nl:needs-human`, `nl:decision`, `nl:discovered`, `nl:stack:<name>`; read the last two with `ts_gh_label decision nl:decision` and `ts_gh_label discovered nl:discovered`), honoring any `labels` overrides.
3. Check the target repo is on its default branch with a clean tree before anything else; if not, stop and tell me.

## Phase 1: dedupe

1. List open TASKS.md items in every section, Decisions and Discovered included. Each has `#<n>` (Discovered items have none), section, stack, text, glyph. A Discovered item's key is `discovered-<8-char sha1 of its normalized text>` (trimmed, whitespace collapsed, lowercased, glyph and sub-bullets excluded), e.g. `printf '%s' "$text" | tr -s '[:space:]' ' ' | tr 'A-Z' 'a-z' | sha1sum | cut -c1-8`.
2. Per item run `ts_find_related <repo> "<short distinctive phrase>"` (open and closed issues). Also search for `Migrated from TASKS.md #<n> (` (Discovered: `Migrated from TASKS.md discovered-<hash> (`; the trailing ` (` keeps `#5` from matching `#50`) so a prior migration run matches (idempotency). For matches that look implemented, dispatch `task-scout` in verify mode (item text, related issues with state, repo path).
3. Decisions and Discovered items skip this step (they have no task branches or PRs). For every other item, whether or not it has an issue match, also check whether the work already shipped, since an item tracked only in TASKS.md has no issue to find. Item numbers are permanent, so the task branch name `overnight/<date>/r<R>-<PP>-t<NN>-<slug>` is the signal:
   - Merged PRs: `gh pr list --repo <repo> --state merged --limit 300 --json number,title,headRefName,mergedAt --jq '.[] | select(.headRefName | test("-t<NN>-"))'`. Fetch the list once and filter it per item rather than calling `gh` per item.
   - Open or closed-unmerged PRs: the same query with `--state open` and `--state closed`. A PR that is open means in flight, not done.
   - Branches: `git -C <repo> branch -a --list '*-t<NN>-*'` for attempts with no PR yet.
   - Any merged PR hit: dispatch `task-scout` in verify mode (item text, the PR numbers, repo path) to confirm the acceptance criteria are on the default branch. Do this only for hits, not for every item.
4. Show each item with its matches (number, state, one-line reason) and ask per match: skip (already tracked), link (create, referencing the match), or create anyway. For an item whose work already shipped, show the merged PR numbers and scout's finding, and offer **archive as done** (default: no issue is created, Phase 4 records it with its PR numbers), or create anyway (for follow-up work scout flagged as missing). Open or unmerged PRs and bare branches are shown as in flight, and I decide whether to skip or create. Items with no matches of any kind proceed. An item I skip is recorded as explicitly skipped.
5. Checked-off items. List every `- [x]` item in any section (a checked Decisions item included), with its sub-bullets. They never become issues. Find each one's PR the same way as step 3 (branch `-t<NN>-`), then fall back to PR numbers or branch names written in the item's own text, and confirm each with `gh pr view <n> --json state,mergedAt`. Show me every item with its PR and merge state and ask: **archive as completed** (default), or treat as open (migrate it like a `[ ]` item) when no merged PR exists and the work isn't on the default branch. An item completed outside a task PR, for example inside other work, is archived as "completed, no task PR" with a one-line note.

## Phase 2: create issues

1. Present the full list of issues to create: title, labels, body. Write nothing until I approve; accept or reject individually.
2. Labels: a Decisions item gets only `nl:decision` (no section label, no stack, so nothing dispatches it); a Discovered item gets only `nl:discovered` (what remote-mode `/discover-tasks` creates and `/plan-tasks` triages). Every other item: section label (`nl:agent-ready`, `nl:verify`, `nl:research`), `nl:stack:<name>` when the item has a stack (not `solo`-less items: `solo` stays `nl:stack:solo`), `[!]` adds `nl:blocked`, `[/]` adds `nl:needs-human`. Missing labels: `gh label create` them (I approved the list above).
3. Body: the task text and acceptance criteria verbatim, a blank line, then `Migrated from TASKS.md #<n> (issue numbers differ from task numbers).` (Discovered: `Migrated from TASKS.md discovered-<hash> (issue numbers differ from task numbers).`) plus any `[!]`/`[/]` annotation, and links for "link" matches.
4. `gh issue create --repo <repo> --title ... --body ... --label ...` per approved item. Record `#<n>` to issue number. Failures: report and stop; nothing flips later.

## Phase 3: review existing unlabeled issues

Read `.claude/skills/tidy-issues/SKILL.md` in the nightlight checkout and follow its steps with labels on (`--labels`), since this repo is moving to the GitHub source. Exclude the issues Phase 2 just created. The gate in its step 3 applies: I can skip the review entirely.

## Phase 4: flip the source

Only after every open TASKS.md item (Decisions and Discovered included) is an issue, was archived as done, or was explicitly skipped by me, every `- [x]` item was archived or sent through as an open item, and phases 2-3 completed without error:

1. Confirm I want to flip and open the PR. Don't proceed without an explicit yes. This yes covers only the flip and the PR, never the merge (step 7 asks separately).
2. Resolve the default branch (`git -C <repo> symbolic-ref --quiet --short refs/remotes/origin/HEAD`, fall back to `main` then `master`); not on it: stop, leave edits uncommitted, tell me.
3. Pull, branch off as `chore/tasks-migrate-<YYYY-MM-DD>` (append `-2`, `-3`... if taken).
4. Move, never delete: write a NEW `docs/tasks-archive/<YYYY-MM-DD>-migrated.md` holding every open TASKS.md item verbatim (Decisions and Discovered under their own headings) with its issue number, "skipped by human", or "already done" with its merged PR numbers and scout's one-line finding, then remove those items from TASKS.md. Checked-off items go in the same file under their own heading, each verbatim with its merged PR numbers (or "completed, no task PR" and the one-line note), and are removed from TASKS.md too. When no item remains (every item is an issue, archived, or explicitly skipped by me), `git rm TASKS.md` entirely; if I skipped any item, keep the file with just those items.
5. Set `"taskSource": "github"` in `docs/nightlight-meta.json`, unless it is already set (create the file with `nextTaskNumber: 1, tasksCompleted: 0, tasksBlocked: 0` if missing, keep existing counters), plus `"github": {"repo": "<owner/name>"}` only if the backlog lives somewhere other than origin.
6. Stage only those files (the archive, the meta file, and TASKS.md edit or removal). Commit `chore(tasks): migrate TASKS.md to GitHub issues`, push, `gh pr create` to the default branch. Then show the PR URL and a diff summary: files changed (`git diff --stat` against the default branch), the archive file's full contents, the `TASKS.md` removals (or its deletion), and the meta change.
7. Ask "merge now?" as its own question, after the step 6 summary is shown. Only an explicit yes merges, with `gh pr merge <branch-name> --rebase --delete-branch` (exact branch name, matching the scoped permission). Anything else, including no answer, leaves the PR open: report it with the URL. A merge failure (required reviews or checks) also leaves the PR open; report it. On success check out the default branch and pull.

Do not implement any code in this session.

## Linear mode (`--to linear`)

Mirrors the flow above with these differences. No `gh issue` or `gh label` calls anywhere; `gh pr list`, `gh pr create`, `gh pr merge` and `git` stay.

- Setup: the same guard (open TASKS.md items decide, not `taskSource`; `taskSource` already `linear` with no open or checked-off (`- [x]`) items: nothing to migrate, stop; already `linear` with open items: run every phase, skip only the flip). Team: `linear.teamId` from the meta file if set. Otherwise call `list_teams`: exactly one team means use it, but tell me its name and key and wait for my yes before anything is created; several teams means list them and ask me which one. Use the team key (for example `C0D`), not the UUID, as `<id>` below and in the meta file. One Linear team per repo is the supported setup: before creating anything, call `list_issues` for the team (a few, newest first) and tell me what it already holds; if any look like they belong to another repo, warn me and stop until I confirm. Shell state does not persist between Bash calls, so every call that uses the module starts with `source lib/task-source.sh && source lib/task-source-linear.sh && export TS_LINEAR_TEAM_ID=<id> && export LINEAR_API_KEY="$(env_get LINEAR_API_KEY <repo> .)"` (`env_get` is from `lib/env.sh`, sourced by `lib/task-source.sh`; if it prints nothing, stop and tell me the key was not found). Use `ts_find_related` and `ts_linear_label` (honoring `labels` overrides; `ts_linear_label decision nl:decision`, `ts_linear_label discovered nl:discovered`). Load the Linear MCP tool schemas (ToolSearch `select:`) for `list_teams`, `list_issues`, `list_issue_labels`, `create_issue_label`, `save_issue`, `save_comment`, `list_issue_statuses`.
- Phase 1: as above. Dedupe with `ts_find_related <repo> "<phrase>"` (prints `<state>	<identifier>	<title>`) and again for `Migrated from TASKS.md #<n> (` or `Migrated from TASKS.md discovered-<hash> (` (keep the trailing ` (`, or `#5` also matches `#50`), so a re-run after a partial migration matches already-created issues and skips them. The shipped-work check is unchanged: `gh pr list --repo <origin repo>` (from `gh repo view --json nameWithOwner`) and `git`.
- Checked-off items: handled exactly as Phase 1 step 5 above. They are archived, never created as Linear issues, and need no Linear calls; the PR lookup uses `gh pr list`, `gh pr view` and `git`. Phase 4 writes them to the archive with their PR numbers and removes them from TASKS.md.
- Phase 2: same approval gate, labels (including the Decisions/Discovered rules) and body. Missing labels: `create_issue_label` (team-scoped, after `list_issue_labels`). Create each issue with `save_issue` (team, title, body, label names or ids); labels set through `save_issue` replace the whole list, so send the full set. Record `#<n>` to the Linear identifier. Failures: report and stop.
- Phase 3: skipped. Reviewing existing unlabeled Linear issues is out of scope (no `/tidy-issues` step in Linear mode).
- Phase 4: as above with `Linear issues` in the archive and commit message (`chore(tasks): migrate TASKS.md to Linear issues`); archive entries carry the Linear identifier. Step 5 sets `"taskSource": "linear"` and `"linear": {"teamId": "<id>"}` unless already set; no `github` block. Same PR, diff summary, and separate "merge now?" confirmation before `gh pr merge <branch-name> --rebase --delete-branch`.
